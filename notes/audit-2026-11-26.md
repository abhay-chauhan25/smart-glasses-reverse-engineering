# Audit of existing research — 2026-11-26

Read-only review of public research before touching the glasses. Nothing was built, run, or sent to a device. Upstream clones were kept outside this repo.

## Plain-language summary

- Someone has already mapped most of how these glasses talk. Their key claims were tested on real glasses, and a second independent project reproduced the main ones. That's a big head start.
- **Easy and proven:** take photos, read battery/versions, get a small preview photo over Bluetooth (~3.5 s), download full-size photos over the glasses' Wi-Fi, stream the microphone.
- **Proven but awkward:** buttons/gestures don't send "pressed" messages. We only see side effects (volume changed, photo taken), so we'll have to be clever.
- **Not proven by anyone:** glasses speakers playing our audio (should work by pairing them to the Mac like earbuds), live video stream (one researcher says yes, another couldn't decode it).
- **Hard:** changing the "Hi Luma" wake word requires firmware changes. Workaround: stream the mic to the laptop and listen for "Hey OMNIS" there.
- **Firmware:** the Bluetooth chip is reportedly a JieLi AC701N; its firmware is scrambled with known keys, so it can probably be studied. The camera/Wi-Fi chip is unknown. Flashing anything is risky with no known recovery.

## Verification of key claims

| Claim | Verdict | Evidence |
|---|---|---|
| BLE service `0000aa12-…`, `aa13` write, `aa14` notify, `aa15` photo notify | Correct, hardware-tested ×2 | Protocol doc §2.1, UUIDs in the decompiled app, manfred notes. Also present: standard Battery Service `180F`, JieLi `AE00/AE01/AE02` |
| Frame: `AB 55` (to glasses) / `AC 55` (from glasses), 2-byte length, command, payload, checksum = byte sum mod 256 | Correct, hardware-tested ×2 | Doc §2.2/§2.4 |
| "60+ commands" | 65 named constants over 61 values; ~20 hardware-tested | `Command.java` (counted) |
| BLE photo 320×180 | Correct ×2, ~3.3–3.6 s | Doc §7.3, manfred. `0x22 [31]` takes a *new* preview photo; button photos never arrive over BLE |
| Wi-Fi full-res 3200×2400 | Correct ×2 | Doc §10.2. Hotspot at `192.168.169.1`, password `12345678`, list at `/app/getfilelist` |
| Mic streaming (Opus) | Hardware-tested | Doc §11.3: `0x57` starts, `0x56` stops, audio on `0x46`, ~40 packets/s, never stops by itself |
| Speaker output via BLE | **No such command** | Doc §11.1. Needs normal Bluetooth audio pairing. Untested by anyone |
| Gesture config | Hardware-tested | Doc §8.1: 5 gestures × 5 actions |
| Live gesture events | **None directly**; side effects visible | Doc §8.1.1, not isolated per gesture |
| "Hi Luma" wake word runs on the glasses | Hardware-tested | Doc §11.2; one unit reported no wake-word support → check ours |
| RTSP live preview | Code exists; claimed 1600×1200 by one researcher; not reproduced | `rtsp://192.168.169.1/h264` in app; manfred couldn't decode |
| Firmware update over HTTP (§10.4) | Only for non-T units; T units use raw TCP `192.168.169.1:5007` | manfred, citing the vendor updater |

## Corrections to earlier assumptions

1. **Upstream tool danger:** `swift run e09_reverse --help` / `--list` are safe. *Any other run, including no arguments*, connects to the first device whose name contains "E09" and runs all 25 tests (photos, settings writes, Wi-Fi, gesture writes). Its README says otherwise; the code (`BleProbe.swift:1670-1678`, commit `863467cd`) wins.
2. The tool's dependencies track `branch: main`, so builds aren't reproducible. Pin before building.
3. The main research repo shows an MIT badge but has no LICENSE file, and it ships a decompiled copy of the vendor app with hardcoded secrets. Don't copy from it.
4. "E09" is a generic name; no FCC ID was found. The real identity is the project/customer code (BLE `0x64`) plus firmware versions.
5. DPVR G6, nisaetus, and OpenSource-Ai-Glasses are **different hardware families**: useful for methods only.
6. Photo parameter names are backwards-looking: `0x22 [30]` "THUMBNAIL" is the normal shutter (saves full photo); `0x22 [31]` "HIGH_QUALITY" makes the 320×180 BLE preview.
7. Advertised 8 MP → originals are 3200×2400 ≈ 7.7 MP.

## Feasibility (short)

| Want | How | Confidence |
|---|---|---|
| Take photo / video | BLE commands | High |
| Quick preview photo | BLE, ~3.5 s | High |
| Full-res photos/videos | Wi-Fi hotspot + HTTP | High (photos), medium (video) |
| Live video | RTSP over Wi-Fi | Medium-low |
| Hear me (mic) | BLE Opus stream | High |
| Talk to me (speaker) | Pair as Bluetooth speaker | Medium (untested) |
| Mic + speaker together | BLE mic in, Bluetooth audio out | Medium |
| Button events | Read side effects / media keys on Mac | Medium-low |
| "Hey OMNIS" wake word | Laptop-side listening on mic stream | Medium (battery?) |
| Firmware wake word | Firmware modification | Low |
| No vendor cloud | BLE + Wi-Fi are local | High |

## Main risks

Different hardware/firmware than researchers' units; accidental firmware update; Mac loses internet while on the glasses' Wi-Fi; battery drain; no real button events; no firmware recovery path; connecting to someone else's glasses (never match by name only).
